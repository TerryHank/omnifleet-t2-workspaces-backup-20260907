## 1. 问题一：网络卡顿与多车信号干涉

**本车现状**：车载 WiFi 路由器 + Jetson；远程可视化走 Foxglove（8765），rosbridge 仅限车端本机。

**课前检查（只读）**：

```bash
ping -c 20 192.168.3.113        # 看延迟与丢包，延迟应 <20ms、丢包 0
ssh iecme@192.168.3.113 'systemctl is-active omnifleet-t2-chassis.service omnifleet-t2-airy.service omnifleet-t2-foxglove.service'
ros2 topic hz /rslidar_points   # 约 5–9 Hz
ros2 topic hz /odom             # 约 10 Hz
```

**多车协同防干涉**：
1. 每辆车在 `/etc/omnifleet_t2/robot.env` 中使用**互不相同的 `ROS_DOMAIN_ID`**（本车当前 73），防止 DDS 串话；
2. 路由器信道错开（2.4G 用 1/6/11，优先 5G），同教室多车不同信道；
3. 天线按原文档方案更换 8 增益棒状天线（已购 12 套）；
4. 根治方案：交换机 + AP 有线 mesh 组网（新华三设备借用仍在争取，到位后车辆改有线接入 AP）。

## 2. 问题二：学生开机自检与"定位准不准"（原文：前轮内八 / EKF）

**⚠️ 配置差异**：T2 是**履带车，没有前轮转向舵机和转向拉杆**，原文档"调短拉杆把前轮调正"的操作在本车不存在、也不需要。履带车的等效机械检查见问题四。

**EKF 不需要学生操作**：本车定位由 MOLA 激光里程计（`map→base_link`）+ 底盘履带里程计（`/odom`）构成，原文档"底层程序未更新导致 EKF 不准"的问题对应本车固件 3.5，已是最新。

**学生开机自检清单（全部只读命令，逐条执行并截图留档）**：

```bash
# ① 一键体检（自带只读体检工具，输出 PASS/WARN/FAIL）
ros2 run omnifleet_bringup robot_doctor

# ② 底盘反馈
ros2 topic echo /odom --once
ros2 topic echo /vel_raw --once
ros2 topic echo /voltage/display --once

# ③ 定位质量与 TF
ros2 topic echo /lidar_odometry/pose_quality --once
ros2 run tf2_ros tf2_echo map base_link
```

**判断定位准不准（对应原文"学生做 EKF 输出准不准"）**：
- 静止测试：车停 1 分钟，`tf2_echo map base_link` 的平移漂移应 < 0.05 m；
- 推算测试：直线推行 1 m，比较 `/odom` 位移增量与 `map→base_link` 位移增量，两者接近（差 < 10%）即定位正常；
- 点云测试：RViz 中看 `/rslidar_points` 与墙面是否贴合、有无"双层墙"（双层说明定位跳变）。

**注意**：`src/omnifleet_tutorials/docs/REMOTE_SELF_CHECK_TREE.md` 中写的 `odom→base_link`、`map→odom` 是旧架构 TF 链，现行 TF 为 `map→base_link` 直发，以本指南为准（该文档待教员更新，本次未改动）。

## 3. 问题三：云台电机烧毁

**本车无云台**：相机与雷达固定在传感器桅杆（`sensor_mast_link`）上，无云台电机，此问题不适用于 T2。

**等效的相机检查**（若图像异常按此排查，学生只查不换）：

```bash
systemctl is-active omnifleet-t2-orbbec-camera.service
ros2 topic hz /camera/color/image_raw    # 预期约 30 Hz
ros2 topic hz /camera/depth/image_raw
```

无图像时：先重启服务 `sudo systemctl restart omnifleet-t2-orbbec-camera.service`，仍无效则检查 USB 线缆并上报教员，**不自行拆机**。若课程使用了其他带云台的车型，云台电机烧毁按原文档执行：直接换新。

## 4. 问题四：掉轮子（履带车等效：履带与行走机构松动）

**每辆车由学生负责，开机自检时目视 + 手动检查**：
1. **履带张紧度**：手指按压履带中段，下垂量约 1 cm 为宜；过松会跳齿脱轨；
2. **履带与链节**：检查有无断裂、缺销、卡入异物；
3. **驱动轮/负重轮紧固件**：中心螺丝与防松螺母是否松动（原理同原文档：防松螺母 + 弹垫，松了用小套筒/十字螺丝刀拧紧，拧紧不会掉）；
4. 紧固后架起车体空转履带一圈确认不刮蹭，再落地低速测试。

**真发生脱轮/脱轨**：立即断电，不再遥控；按摆臂结构复位履带后由教员确认，再上电测试；记录车辆编号与原因（对应原文档"学生自己负责自己的车"）。

## 5. 问题五：程序运行异常与还原

本车没有 `dzrobot` 压缩包，还原路径按以下顺序（学生只做第 1 步，其余找教员）：

**① 重启服务（多数异常可恢复）**：

```bash
sudo systemctl restart omnifleet-t2-chassis.service omnifleet-t2-airy.service
# 导航在跑且异常时：
sudo systemctl restart omnifleet-t2-navigation.service   # 或直接 stop
```

**② 单文件被误改**：从工作区 `backups/` 按日期找回对应文件（如 `backups/direct-mola-tf-20260902-185518/` 内保存有 `nav2_t2.yaml`、驱动、launch 的历史版本），覆盖回 `src/` 后重新编译：

```bash
cd /home/iecme/workspace/omnifleet_t2_ws && colcon build --symlink-install   # 仅教员执行
```

**③ 整体回退**：完整旧工作区在 `/home/iecme/omnifleet_migration_backups/20260901_212317_pre_omnifleet_t2`；`SOURCE_MANIFEST.sha256` 可校验源码是否被改动。

**④ 还原后验收**：`ros2 run omnifleet_bringup robot_doctor` 全部 PASS 方可继续使用。

**课程纪律（同原文档）**：此类异常报错各不相同，无固定报错内容，唯一可靠办法是还原；学生改动任何文件前必须记录文件名和改动内容，未经允许不得改 `src/` 与 `/etc/omnifleet_t2/`。

## 6. 问题六：ROS 学习内容（建图 + 导航基础）与 TF 讲解

**本车最小必学话题集**：

| 话题 | 类型 | 作用 |
|---|---|---|
| `/rslidar_points` | PointCloud2 | 3D 激光点云（建图/避障输入） |
| `/odom` | Odometry | 履带里程计（底盘驱动发布） |
| `/map` | OccupancyGrid | 栅格地图（MOLA 局部地图，0.1 m/格） |
| `/tf` `/tf_static` | TFMessage | 坐标系变换 |
| `/cmd_vel` | Twist | 速度指令（仅 controller_server / behavior_server 可发） |
| `/initialpose` `/goal_pose` | PoseStamped | 初始位姿 / 导航目标 |
| `/plan` `/local_plan` | Path | 全局 / 局部路径 |

**实际 TF 树（现行架构，上课按这个讲）**：

```
map ──(MOLA 激光里程计，动态)──▶ base_link
base_footprint ─(静)─▶ base_link ─(静)─▶ rslidar / camera_link / imu_link
                                   ├─(静)─▶ left_track_link / right_track_link
                                   └─(静)─▶ sensor_mast_link
```

- TF 中**没有 odom 帧**；`/odom` 话题仍存在，但坐标系融合结果由 MOLA 直接以 `map→base_link` 输出（等价于教科书 `map→odom→base_link` 的合并形式）。
- 讲课演示（对应原文档"把 odom 到 baselink 的由来讲清楚 + 录 TF 标定视频"）：
  1. RViz `Fixed Frame=map`，添加 TF + RobotModel，推车观察车模型随动；
  2. 终端 `ros2 run tf2_ros tf2_echo map base_link`，推车看数值变化，讲"激光配准算出车在地图中的位姿"；
  3. 遮挡雷达再推车，观察 TF 漂移，讲定位退化。

**建图 → 保存 → 导航完整流程（教员演示）**：

```bash
cd /home/iecme/workspace/omnifleet_t2_ws
ros2 launch omnifleet_bringup production.launch.py \
  backend:=mola map_id:=active \
  map_dir:=/var/lib/omnifleet_t2/maps \
  start_description:=false
# 或 systemd 方式：sudo systemctl start omnifleet-t2-navigation.service

ros2 lifecycle get /bt_navigator      # 预期 active
ros2 lifecycle get /planner_server    # 预期 active
ros2 lifecycle get /controller_server # 预期 active
ros2 topic echo /map --field info --once
```

地图保存/加载：服务 `/map_save`、`/map_load`（Foxglove 白名单已放行），或航点面板话题 `/omnifleet_t2/waypoints/map_save`、`/omnifleet_t2/waypoints/map_load`；MOLA 地图工件为 `local_map.mm`。

## 7. 问题七：导航初始定位问题（实车 + 虚拟仿真）

**原因 1（建图时车不在原点）同样适用**：开始建图前把车摆在预定原点，或记住摆放点，导航从该区域启动。

**初始定位不准的标准处理**：
1. RViz 用 **2D Pose Estimate**（发布 `/initialpose`）在地图上拉出真实位姿；Foxglove 客户端白名单已放行 `/initialpose`；
2. 拉了没效果 → 重启导航（终端 Ctrl+C 或 `sudo systemctl restart omnifleet-t2-navigation.service`）再拉一次（与原文档"重启程序就恢复"的处置一致）；
3. 仍无效 → 记录时间、车辆编号、操作步骤，交浩强/贺瑞复现排查（原文档遗留的随机问题，未解决前统一按此流程）。

**虚拟仿真端**：本工作区含 `omnifleet_simulator`（ros_gz_bridge）。仿真实验前确认：仿真车模型摆在世界原点、对应节点 `use_sim_time:=true`；现象与原理演示为主，参数保持默认不改（对应原文档"虚拟仿真目的是看现象、学原理"）。

## 8. 问题八：只给学生调"一调就见效"的参数

系统已在 Foxglove 参数白名单（`/etc/omnifleet_t2/foxglove.yaml`）中做了限定。**建议课程只开放以下 3 个**（符合原文档"障碍物膨胀半径 + 某一两个参数"的要求）：

| 参数 | 所在位置 | 当前值 | 建议范围 | 直观效果 |
|---|---|---|---|---|
| `inflation_radius` | local/global costmap 的 `inflation_layer` | 0.3 m | 0.2 – 0.6 m | 调大：离障碍更远、更早绕行、门缝不过 |
| `cost_scaling_factor` | 同上 | 5.0 | 1 – 10 | 调小：代价衰减慢，路径整体更远离障碍 |
| `max_vel_x`（FollowPath/DWB） | `controller_server` | 0.1 m/s | ≤ 0.3 m/s | 直接改变车速，效果立竿见影 |

**操作方法（学生可做）**：Foxglove 连接 `ws://192.168.3.113:8765` → Parameters 面板修改，即时生效；观察 Local Costmap 膨胀圈和实车绕行行为的变化。想保留修改时由教员调用 `/omnifleet_t2/nav2/save_parameters` 服务固化（白名单已放行）。

**红线**：footprint、`xy_goal_tolerance`（0.25 m）、加减速限制等安全相关参数不开放；不允许学生直接改 `nav2_t2.yaml` 后自行重编译（改坏按问题五还原流程处理）。

## 9. 问题九：RViz / 可视化界面说明

**RViz 推荐配置（Fixed Frame = map；导航未启动时用 odom 系数据）**：

| Display | 话题/内容 | 用途 |
|---|---|---|
| OccupancyGrid | `/map` | 栅格地图 |
| Costmap | `/global_costmap/costmap`、`/local_costmap/costmap` | 全局/局部代价地图（看膨胀效果） |
| PointCloud2 | `/rslidar_points` | 实时点云 |
| Path | `/plan`（全局）、`/local_plan`（局部） | 规划路径 |
| Polygon | `/local_costmap/published_footprint` | 车体轮廓 |
| RobotModel + TF | — | 车模与坐标系 |

交互按钮：**2D Pose Estimate** → `/initialpose`（设初始位姿）；**2D Goal Pose** → `/goal_pose`（发导航目标，需导航栈 active）。

**Foxglove（推荐，已有 T2 专用布局）**：五面板（点云、车模、电压 `/voltage/display`、IMU `/imu/data_raw`、`/odom`）+ 地图/代价地图；固定参考系 `odom`，避免导航未启动时 `map` 系不存在导致白屏。控制器/规划器切换：发布 `/controller_selector`、`/planner_selector`（String，白名单已放行）。

**航点面板**：`omnifleet_t2_waypoint_ui` + 话题 `/omnifleet_t2/waypoints/*`（add_pose / next_name / rename / navigate_to / start / stop / undo / clear / status / catalog）。

## 附录 B：安全红线

1. 状态查询不授权运动：非课程实验环节，不发布 `/cmd_vel`、不发 `/goal_pose`、不调用有运动副作用的服务；
2. 停止导航：先用航点面板 stop / Foxglove 取消目标，必要时 `sudo systemctl stop omnifleet-t2-navigation.service`；**微信 /stop 只取消 AI 任务，不是机器人急停**；
3. 急停 = 断底盘电源；
4. 一切参数与文件修改须经教员确认，改前在 `backups/` 留档；导航服务保持 disabled，不随开机自启。
