## DSH 超时真实原因与修复

原失败请求 `7a91a5b3-dd87-41ab-a9b6-29ad43a82ebb`：采集 0.185 s，模型 HTTP 200 响应约 1.266 s，之后生成到 120.122 s 被截止。旧计时代码把 reasoning_content 和可读 content 都记为 first_model_token，因此“已开始生成”不能证明已经产生最终答案。

进一步实测发现调用模型为 `qwen3.8-max`，原请求没有设置推理力度/预算，输出上限 32768。无预算的一次复测等待约 42.155 s 才出现可读答案，完整流程约 58.119 s。阿里云官方说明该模型未指定力度时使用默认 xhigh，并支持 thinking_budget；两者不能同时设置。[官方参数说明](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)

修复只作用于 Foxglove 的只读诊断子进程：

- Qwen3.8 请求设置 `thinking_budget=2048`、`max_tokens=6144`，清除互斥的 reasoning_effort；正常 DSH 会话和默认模型没有改动。
- 区分模型连接、推理开始、可读答案开始、结束、用量和总耗时；只记录计数/时间，不记录密钥或推理正文。
- 不向模型提供工具入口；诊断依据由 ROS 快照提供。
- 仅说“我先检查”的准备性文本不再显示为“诊断完成”。缺少规定结论分组时，在原时间预算剩余范围内做一次格式重试，仍不完整则报错。
- 快照增加公共地图、两车状态和运行参数，明确 113 参数面板归属；不要求用户点击未安装的车队面板或 104 参数面板。
- 软件停车和运动锁由实际快照解释，禁止把软件 estop 当成物理急停已按下的证据。

最终通过真实 Foxglove WebSocket/CDR 链路提交问题，**38.681 s 收到完整分项答案**：模型连接 1.374 s、首次可读内容等待 23.626 s、答案生成 9.820 s，总后端耗时 37.268 s；只使用一次模型请求。此前两次完整 WebSocket 回归分别约 42.7 s、50.8 s。结果不能保证所有问题永不超时。

证据：`websocket-diagnostic.json`、`diagnostic-before-policy.log`、`diagnostic-after-policy.log`。协议验证时曾误用旧 `foxglove.websocket.v1` 得到失败，随后依据安装库和官方定义改为 `foxglove.sdk.v1`，成功收到 109 个频道；未为此重启或修改 Foxglove bridge。

- 无可达等待点/重组点时系统停队报告原因，不强行执行后退或宣称死锁已解除。
- 没有专用车队控制面板或 104 参数面板；本版提供 CLI、标准 ROS 话题与 113 的 DSH 诊断接入。
